**Runbook — ajouter un nouveau client (décision 2026-07-06 : à la demande, pas de structure pré-créée):**
1. `docker exec -u www-data nextcloud php occ group:add client-<slug>`
2. Créer le compte : `occ user:add --group="client-<slug>" <username>` (ou utiliser l'app `guests` déjà activée pour un compte allégé externe)
3. `occ groupfolders:create "<Nom Client>"` → récupérer l'ID retourné
4. `occ groupfolders:group <ID> client-<slug> read write share delete` (**syntaxe correcte confirmée empiriquement 2026-07-07 : liste de mots séparés par des ESPACES, PAS des virgules** — `read,write,share,delete` échouerait silencieusement ou serait mal interprété ; mots valides : `read`/`write`/`share`/`delete`, `write` inclut déjà UPDATE+CREATE)
5. Optionnel : `occ groupfolders:quota <ID> <Go>` pour limiter l'espace

**Structure interne "3 équipes × 2 groupes" mise en place le 2026-07-07 (RH, Compta, SI)** — pattern réutilisable pour toute nouvelle équipe interne : 2 groupes par équipe (`<equipe>-manager`, `<equipe>-utilisateur`), 1 Groupfolder par équipe, droits différenciés : manager = `read write share delete` (contrôle total), utilisateur = `read write` (pas de partage externe ni de suppression — le manager reste le seul point de contrôle sur qui accède au dossier depuis l'extérieur). Folders créés : RH=id 1, Compta=id 2, SI=id 3. **Ne pas confondre avec Circles/Teams** : les Groupfolders ne prennent des permissions que via des Groupes classiques, pas via des Circles — donc pour toute demande de ce type ("créer une équipe avec des droits sur un dossier"), toujours passer par `occ group:add`, jamais par Circles. **Comment ça marche en interne (important si on retouche la structure) :** la hiérarchie Collectives n'est QUE la structure de dossiers Nextcloud standard, lue en direct — `oc_collectives_pages` n'a AUCUNE colonne de parent, juste `file_id` (+ emoji/tags/slug/trash_timestamp/subpage_order qui n'est qu'un indice d'ordre cosmétique). Une "page-dossier" = un vrai dossier + un `Readme.md` dedans dont le `file_id` a une ligne dans `oc_collectives_pages`. Conséquences pratiques :
- **Créer** une nouvelle page nécessite `PageService` (pas d'event listener sur la création de fichier — seuls `NodeRenamedEvent`/`NodeWrittenEvent` sont écoutés) → passer par `occ collectives:import:markdown` (fiable) plutôt que d'appeler `PageService::create()` à la main (a échoué avec `NotFoundException: File not found: 0` dans un script bootstrap manuel — le contexte `OC_Util::setupFS()` seul ne suffit pas à ce que `PageService` attend ; cause exacte non résolue, ne pas perdre de temps dessus, contourner via CLI).
- **Déplacer/renommer** une page existante marche très bien en Files API brute (`$rootFolder->getById($fileid)[0]->move($nouveauChemin)`) — pas besoin de `PageService`, le rename/move déclenche `NodeRenamedEvent` et Collectives se met à jour tout seul. C'est la méthode utilisée pour classer les 20 pages dans les 5 dossiers.
- **Piège vécu** : après un `PageService::trash()` réussi, le fichier physique n'est PAS immédiatement déplacé vers la corbeille (seul `trash_timestamp` est posé) — le nom reste occupé, donc une ré-importation du même titre juste après prend un suffixe `(2)`. Attendre / vérifier via `oc_filecache` avant de réimporter le même nom.
- **Piège verrou** : un déplacement peut échouer avec `OCP\Lock\LockedException` si le fichier a un verrou applicatif orphelin (pas forcément un onglet ouvert — un script précédent qui plante en cours d'écriture peut laisser un verrou orphelin, `ttl` en base n'est PAS vérifié à la lecture par `DBLockingProvider::isLocked()`, donc rien ne l'expire automatiquement). Fix : `$node->unlock(\OCP\Lock\ILockingProvider::LOCK_EXCLUSIVE)` et `LOCK_SHARED` via un script bootstrap, avant de retenter le `move()`.

Technique d'import (pages plates) : `occ collectives:create "<nom>" --owner=<user>` (pas d'ID retourné en CLI — le récupérer via `SELECT id FROM oc_collectives` en DB), puis rédiger les `.md` localement et `occ collectives:import:markdown <dossier> --collective-id=<ID> --user-id=<user> --parent-id=0`. Penser à `occ collectives:generate-slugs` après import pour que les liens `[[...]]` se résolvent. Les fichiers vivent dans `data/appdata_*/collectives/<ID>/*.md` (pas dans le Files personnel de l'utilisateur) — mais le chemin est aussi accessible via `getUserFolder('adininfo')` sous `/adininfo/files/.Collectifs/<Nom collective>/`.

**Découverte technique majeure — pourquoi certains services Nextcloud échouent en script CLI même avec `OC_Util::setupFS($userId)` seul (explique aussi l'échec `PageService::create()` rencontré plus tôt avec Collectives, jamais élucidé à l'époque) :** certains services (Tables `PermissionsService`, probablement Collectives `PageService` aussi) ont un `?string $userId` injecté par le conteneur DI de Nextcloud, lié à **la session utilisateur courante** (`IUserSession`) — PAS au paramètre qu'on passe explicitement à la méthode appelée. Un simple `OC_Util::setupFS($userId)` monte le filesystem de cet utilisateur mais n'établit PAS de session applicative, donc ce `$userId` injecté reste `null`, et des méthodes internes profondes (ex : `TableService::create()` → `enhanceTable()`) qui appellent `preCheckUserId()` **sans repasser le userId qu'on a fourni en surface** tombent sur ce `null` et échouent. **Fix qui marche à chaque fois** : avant de résoudre le moindre service du conteneur DI, faire :
```php
$user = \OC::$server->get(\OCP\IUserManager::class)->get($userId);
\OC::$server->get(\OCP\IUserSession::class)->setUser($user);
\OC_Util::setupFS($userId);
```
Puis résoudre les services APRÈS cet appel (pas avant, sinon des instances déjà construites gardent un `$userId` figé à `null`). Cette technique doit désormais être systématique pour tout nouveau script bootstrap touchant une app tierce (Collectives, Tables, ou une future app) — elle aurait évité l'écueil documenté plus haut sur `PageService::create()`.

**Piège vécu — tentatives ratées avant le fix laissent des tables fantômes :** avant de trouver le fix ci-dessus, 4 tentatives de création de table ont échoué en PermissionsService APRÈS l'insertion en base (l'insert de la table elle-même se produit avant l'appel `enhanceTable()`/`makeTemplate()` qui plante) — résultat : 4 tables vides "Bibliothèque de documents" fantômes (colonnesCount=0) créées silencieusement en plus de la bonne. **Bug d'infrastructure trouvé et corrigé 2026-07-07 : ouverture d'un .xlsx (Collabora) restait bloquée sur "Chargement..." indéfiniment.** Cause racine : le vhost nginx `nextcloud.conf` (`/home/proxy/nginx/conf.d/`, édité depuis l'intérieur du conteneur `proxy-nginx` qui tourne en root) ne supportait PAS les WebSockets — aucun header `Upgrade`/`Connection`, pas de `proxy_http_version 1.1`. 1. 2. Dans `nextcloud.conf`, ajout dans le bloc `location /` : `proxy_http_version 1.1;`, `proxy_set_header Upgrade $http_upgrade;`, `proxy_set_header Connection $connection_upgrade;`, `proxy_read_timeout 3600s;`, `proxy_send_timeout 3600s;`.
3. Déploiement propre : écrire le fichier en LOCAL puis `docker cp` (le heredoc imbriqué `ssh → docker exec sh -c → heredoc` corrompt les `$variables` nginx à travers les multiples couches d'échappement shell — confirmé empiriquement, ne jamais retenter cette approche pour du contenu avec des `$` : toujours écrire en local et `docker cp`).
4. `nginx -t` puis `nginx -s reload` (pas de coupure de service).

**RÉSOLUTION DÉFINITIVE du blocage Collabora "Chargement..." infini (2026-07-07) — historique complet, le fix `public_wopi_url` seul (ci-dessous, tenté d'abord) s'est révélé INSUFFISANT, vraie cause trouvée ensuite :**

Étape 1 (fix WebSocket nginx) : nécessaire mais pas suffisant, voir plus haut.

Étape 2 (fausse piste partielle) : la **console développeur du navigateur** a montré :
```
Connecting to 'http://localhost/custom_apps/richdocumentscode/proxy.php?status' violates the following
Content Security Policy directive: "connect-src 'self' blob: stun.nextcloud.com:443". The action has been blocked.
```
J'ai d'abord cru que régler `occ config:app:set richdocuments public_wopi_url --value='https://nextcloud.noschoixpourvous.com/...'` suffirait (théorie : `wopi_url`=serveur-à-serveur vs `public_wopi_url`=navigateur, `getCollaboraUrlPublic()` retombant sur `wopi_url` si non défini). **Ce fix seul n'a PAS résolu le problème** — même erreur CSP reproduite par l'utilisateur après coup.

**Vraie cause racine (trouvée en lisant le code source de richdocuments dans le conteneur, pas la doc) :** le XML de découverte Collabora (`/hosting/discovery`, servi par le process `coolwsd` embarqué dans `richdocumentscode`) **embarque littéralement l'hôte de la requête qui l'a fetché** dans les URLs `urlsrc` renvoyées (confirmé empiriquement : `curl -H 'Host: nextcloud.noschoixpourvous.com' .../discovery` change immédiatement le `urlsrc` retourné). Or `DiscoveryService::getDiscoveryEndpoint()` (dans `lib/Service/DiscoveryService.php`) construit toujours l'URL de fetch à partir de **`wopi_url` seul** (jamais `public_wopi_url` — cette clé ne sert QUE pour les headers CSP dans `Capabilities.php`, pas pour construire les `urlsrc`). Donc tant que `wopi_url` valait `http://localhost/...`, le XML de découverte — mis en cache (`CachedRequestService`, cache distribué + fichier appdata, TTL 3600s) — embarquait `localhost` dans TOUTES les URLs d'éditeur envoyées ensuite au navigateur, quoi qu'on mette dans `public_wopi_url`. Bug 100% silencieux côté serveur (`nextcloud.log` ne log jamais rien ici).

**Piège du fix naïf "juste mettre `wopi_url` sur le domaine public" :** déjà tenté avant dans la session (voir plus haut, ligne "Piège WOPI Collabora") et cassait la génération d'aperçus avec un 403 — parce que l'appel PHP sortant partait vraiment sur Internet (Cloudflare Tunnel aller-retour).

**Fix définitif appliqué : garder `wopi_url` = domaine public, mais faire résoudre ce domaine EN INTERNE dans le conteneur `nextcloud`, sans jamais sortir sur Internet :**
1. `docker-compose.yml` (`/home/projet_nextcloud/docker-compose.yml`) : ajout `extra_hosts: - "nextcloud.noschoixpourvous.com:host-gateway"` sur le service `app` → écrit `[IP-INTERNE] nextcloud.noschoixpourvous.com` (IPv4 uniquement, IP de la passerelle Docker = l'hôte) dans `/etc/hosts` du conteneur. `docker compose up -d app` pour recréer le conteneur avec ce mapping (downtime de quelques secondes).
2. `proxy-nginx` publie déjà les ports 80/443 sur l'hôte (`0.0.0.0:80/443`, vérifié via `docker port proxy-nginx`) — donc la requête HTTPS sortante du conteneur `nextcloud` vers `nextcloud.noschoixpourvous.com` atterrit sur `host-gateway:443`, qui est en fait `proxy-nginx` écoutant sur l'hôte, qui la reproxy vers `http://nextcloud:80` (le même conteneur) — boucle 100% interne au réseau Docker, jamais de sortie Internet, donc plus de risque de 403 Cloudflare.
3. **Piège IPv6 rencontré** : `extra_hosts`/`host-gateway` n'écrit qu'une entrée IPv4. Le conteneur a aussi une résolution DNS publique active pour ce domaine côté IPv6 (adresses Cloudflare réelles en `2a06:98c1:...`), donc un `getent hosts` ambigu montrait les IPv6 publiques. Vérifié avec `curl -6` (échoue proprement, "Couldn't connect", pas de vraie connectivité IPv6 sortante donc pas de risque de fuite silencieuse) et `curl -4` (200, passe bien par `[IP-INTERNE]`) — la résolution par défaut (sans -4/-6) utilise bien la voie IPv4 interne grâce au fast-fail IPv6.
4. `occ config:app:set richdocuments wopi_url --value='https://nextcloud.noschoixpourvous.com/custom_apps/richdocumentscode/proxy.php?req='` (et `public_wopi_url` à la même valeur, désormais redondant mais inoffensif).
5. `occ richdocuments:activate-config` pour vider le cache de découverte et re-fetcher — **premier appel peut timeout à 5s (erreur `cURL error 28`) si le process `coolwsd` n'est pas encore chaud** (démarrage paresseux au premier appel, peut prendre 10-30s) ; relancer une seconde fois après un `curl --max-time 30` de warm-up suffit.
6. Vérifié : `curl .../hosting/discovery` renvoie désormais `urlsrc="https://nextcloud.noschoixpourvous.com/..."` (plus jamais `localhost`), ET `occ preview:generate <fileId>` fonctionne toujours (pas de régression sur l'usage serveur-à-serveur, qui passe maintenant aussi par le domaine public en interne).

**Architecture HPB (serveur de signalisation haute performance) + TURN déployée le 2026-07-07** pour supprimer l'avertissement "Configuration de Talk incomplète" et permettre de vrais appels multi-participants externes (au-delà du peer-to-peer nu) :

- **Contrainte de départ** : la VM homelab est derrière un routeur domestique (IP locale `[IP-INTERNE]` → IP publique `93.23.16.67` via NAT ISP) — pas de port-forwarding possible sans accès au routeur. Piste explorée puis abandonnée avant implémentation — **ne pas reproposer cette approche**.
- **Solution retenue : split d'hébergement.**
  - **coturn (TURN/STUN)** hébergé sur le **VPS IONOS de ConfIA** (`[IP-VPS]`, voir [[project_confia_ovh]]) — IP publique directe sans NAT, contrôle total du pare-feu, contrairement au homelab. Range de relais restreinte à 40 ports (`49160-49200`) plutôt que la plage par défaut énorme, pour limiter la surface exposée. `denied-peer-ip` sur toutes les plages RFC1918/loopback/link-local pour empêcher le relais TURN de servir de proxy vers le réseau interne (anti-SSRF).
  - **Pare-feu IONOS** : au-delà de l'OS (iptables, policy ACCEPT par défaut, rien à faire côté OS), IONOS a un **pare-feu réseau séparé au niveau Cloud Panel** ("Stratégies de pare-feu", menu Réseau) qui bloque tout par défaut sauf règles explicites — piège vécu : le port TCP 3478 tournait bien localement (confirmé via `ss`) mais restait injoignable depuis l'extérieur tant que les règles n'étaient pas ajoutées manuellement dans ce panneau web (pas d'API/CLI trouvée pour ça, uniquement le Cloud Panel : `cloudpanel.ionos.fr` → serveur → section "Stratégies de pare-feu"). Règles ajoutées : TCP 3478, UDP 3478, UDP 49160-49200 (source "tous"). 1. Ghostscript (`gs`) absent du conteneur — nécessaire comme delegate PDF pour ImageMagick/Imagick (le module PHP `imagick` lui-même était déjà présent et chargé, juste le binaire système manquant). Ajouté au `Dockerfile` custom (voir ci-dessous).

**4ᵉ bug trouvé sur le même chantier OCR (le vrai bloqueur final)** : `Pdf::save($tmpPath)` de `spatie/pdf-to-image` v3 ne respecte PAS le chemin donné tel quel — `PdfPage::filename()` reconstruit le nom en ajoutant l'extension du format (`.jpg`) via `pathinfo()`, donc `save('/tmp/phpXXXXXX')` écrit en réalité sur `/tmp/phpXXXXXX.jpg` (un fichier SIBLING different), tout en laissant le fichier d'origine (`tmpfile()`) vide. `TesseractService.php::ocrPdf()` continuait d'appeler Tesseract sur le chemin ORIGINAL (vide) — symptôme Tesseract : `Error in findFileFormatStream: truncated file`, capturé silencieusement par le try/catch (`$result = ''`), donc zéro erreur visible sans passer le loglevel a 0 (debug) pour voir les logs `notice`. **Fix** : capturer la valeur de retour de `save()` (un `array` des chemins réellement écrits) et OCR-iser ce chemin réel, pas l'original — patch dans `ocrPdf()` (méthode complète, 4 lignes ajoutées) : `$savedPaths = $pdf->save($tmpPath); $actualPath = $savedPaths[0] ?? $tmpPath; $content .= $this->ocrFileFromPath($actualPath);` + nettoyage du fichier réel via `unlink($actualPath)` (le `fclose($tmpFile)` existant ne supprime que le fichier ORIGINAL vide, pas le `.jpg` réellement écrit — sans ce nettoyage ajouté, chaque page OCR-isée laisserait un fichier orphelin dans `/tmp`). **Piège méthodologique qui a débloqué ce diagnostic** : passer temporairement `occ config:system:set loglevel --value=0` (DEBUG) le temps du test, car au niveau par défaut (2, WARNING) l'exception réelle de Tesseract (loggée en `notice`, niveau 1) est invisible — remonter `loglevel` a 2 juste après. Reproduit et confirmé via un script isolé appelant `ocrPdf()` par réflexion sur un vrai `OCA\Files_FullTextSearch\Model\FilesDocument` (PAS le générique `IndexDocument` du provider Collectives — mauvais type au premier essai, `TypeError` immédiat) avec `setMimetype('application/pdf')` positionné manuellement (sinon le tout premier garde-fou de `ocrPdf()` retourne `false` sans rien tenter).

**3ᵉ bug trouvé sur le même chantier OCR, après le patch API ci-dessus** : `tesseract_lang` doit être renseigné en **virgules** (`fra,eng`), PAS avec la syntaxe `+` native de tesseract (`fra+eng`) que j'avais posée initialement par réflexe CLI. Le wrapper PHP `thiagoalessio/tesseract_ocr` fait `explode(',', $config)` puis passe chaque langue comme argument séparé à `TesseractOCR::lang(...$langs)` (qui recolle avec `+` en interne pour construire la commande réelle) — avec `fra+eng` non séparé, `explode` renvoie un seul élément invalide, `tesseract -l fra+eng` échoue silencieusement (exception catchée, contenu OCR mis à `''`), et rien ne remonte dans les logs par défaut. Symptôme observé : reindex complet "0 erreur" mais `parts.ocr` vide dans Elasticsearch pour tous les documents — vérifié en inspectant directement le document ES (`curl localhost:9200/<index>/_doc/files:<id>`), le champ `content` seul ne suffit pas à diagnostiquer ce genre de app custom qui écrit dans un "part" séparé plutôt que le contenu principal. **Leçon consolidée avec le bug API ci-dessus** : pour toute app tierce Nextcloud dont le comportement semble "silencieusement inopérant" malgré une config qui a l'air correcte, toujours (1) isoler l'appel réel via `php -r` inline pour voir la vraie exception, (2) vérifier le format EXACT attendu par le code de l'app pour chaque valeur de config (ne jamais supposer la syntaxe native de l'outil sous-jacent), (3) inspecter le document final dans le datastore cible (ici Elasticsearch) plutôt que de se fier au log applicatif seul.

**Recherche par sens v2 : architecture finder + ranker (2026-07-14, commit 7415763).** Suite à la question "comment améliorer la pertinence, Sinequa parle de spliter ranker et finder" + demande explicite "les deux, j'aimerais que ma solution soit une vraie valeur ajoutée, documentée et schématisée" — implémenté les deux volets proposés :
- **Finder amélioré (passages/chunking)** : `embed_backfill.php` découpe désormais chaque document éligible en passages de ~900 caractères (chevauchement 150) au lieu d'un seul vecteur sur les 800 premiers caractères — corrige un vrai défaut (un document long dont le passage pertinent est au milieu/à la fin était invisible en recherche par sens). Chaque passage = document ES léger séparé (`<provider>:<id>:p<n>`) avec copie des champs d'accès du parent (le filtre ACL s'applique passage par passage). **Plafond de 40 passages/document découvert nécessaire en test réel** : un livre PDF de 2.8 Mo ("Intelligence artificielle" John Paul Mueller) a produit 1182 passages à lui seul avant ce plafond, ralentissant le backfill de façon disproportionnée — échantillonnage uniforme sur tout le texte au-delà du plafond (pas juste le début).
- **Ranker (reranking LLM)** : `SearchController::rerankWithLLM()` — les ~15 meilleurs candidats du finder sont envoyés en UN SEUL appel LLM (`llama3:8b`, réutilise le modèle déjà en place pour l'Assistant IA) qui les reclasse par pertinence réelle. Fallback silencieux sur l'ordre kNN si la réponse n'est pas parsable. **Coût mesuré : ~20-22s** pour reclasser 8-15 candidats sur ce serveur CPU sans GPU — message de chargement adapté côté frontend, rate-limit resserré à 30/min (au lieu de 60) sur cet endpoint spécifiquement à cause du coût LLM.
- `searchNeural()` regroupe maintenant les hits kNN par document PARENT (meilleur passage = score du document), va chercher les métadonnées du parent (titre/tags/date) via un `_mget` groupé (`fetchParentMetadata()`, même principe que `fetchChapterMap()`) puisque les passages n'ont pas de titre propre. L'extrait affiché par résultat est désormais le **passage réellement le plus proche sémantiquement** (label "Passage le plus pertinent"), pas une heuristique sur le contenu complet.
- **Documentation étendue avec schémas** dans la page wiki "23 Architecture de Recherche+" : explication du kNN ("k plus proches voisins", analogie carte géographique), schéma finder+ranker complet, section sur les 3 sources de bruit déjà neutralisées (dossiers vides/photos/démo Nextcloud — récapitulatif consolidé), limites connues (batch size embedding, plafond passages, ranker faillible).
- Testé de bout en bout via script bootstrap avant déploiement (finder retrouve bien le bon document en top, ranker fonctionne et prend ~22s, cohérent avec ce qui est communiqué à l'utilisateur).

**Recherche par sens v3 : mxbai-embed-large + découpage récursif (2026-07-14, commit 677662b).** Suite à "pas d'autre outil open source pour les gros documents ?" puis "go pour les deux et documente ces choix" :
1. **Cause racine du plantage Ollama enfin identifiée** : ce n'était PAS une vraie limite du modèle nomic-embed-text, mais la taille de BATCH par défaut du serveur d'inférence (512) — `options.num_batch=4096` passé à l'appel élimine le plantage, testé jusqu'à 16 000 caractères sans dégradation de temps notable. Découverte en testant méthodiquement (pas en lisant une doc).
2. **Changement de modèle** : `nomic-embed-text` (768 dim) → `mxbai-embed-large` (1024 dim, déjà installé sur Ollama). Vérifié via recherche externe (pas supposé) : état de l'art MTEB pour sa catégorie, dépasse même text-embedding-3-large d'OpenAI sur ce benchmark. Testé empiriquement plus rapide (0.1-0.5s vs 0.7-1.8s) ET encaisse 12 000 caractères SANS même avoir besoin de num_batch. **Convention de préfixe différente et vérifiée via la doc Ollama officielle** (pas devinée) : contrairement à nomic (préfixe des deux côtés), mxbai n'attend AUCUN préfixe côté document/passage — seule la requête reçoit `"Represent this sentence for searching relevant passages: "`.
3. **Piège ES rencontré en migrant** : Elasticsearch refuse de changer les `dims` d'un champ `dense_vector` existant, même vide (`Cannot update parameter [dims] from [768] to [1024]`, vérifié directement) — nouveau champ `embedding_vector_v2` créé en parallèle, `embedding_vector` (768, ancien) laissé inutilisé.
4. **Découpage récursif** (remplace le découpage brut au nombre de caractères) : paragraphes → phrases → brut en dernier recours, même philosophie que `RecursiveCharacterTextSplitter` de LangChain, réimplémenté en PHP (pas de nouvelle dépendance). Chunk size relevé à 6000 caractères (dans la plage réellement entraînée du modèle), plafond passages/document relevé de 40 à 200 (le vrai coût d'avoir plus de passages est juste la durée du backfill nocturne, pas la vitesse de recherche — leçon retenue après avoir fixé 40 par réflexe de prudence sans évaluer ce coût réel).
5. **Backfill complet relancé proprement** (226 documents, 450 passages, 0 erreur) après avoir supprimé les anciens passages nomic (éviter tout travail en double avant de valider le choix du modèle).
6. **Vérifié en test réel** : un document peut légitimement changer de position (1re → 6e) entre deux modèles d'embedding sur la même requête — ni l'un ni l'autre n'est "faux", c'est précisément pour ça que le ranker LLM existe (corriger ce genre d'écart).
